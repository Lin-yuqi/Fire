目标是理解每一步为什么测、数据说明什么，再决定是否修改代码。每次只推进一个步骤，完成后解释结果，等用户指定下一步再继续。

下列步骤保留为后续单项优化的工作方式，不自动执行整套流程。

## 执行步骤

### 1. 明确测量对象与计时口径

沿着 `demo/qwen_chat.cpp` 讲清楚一次请求的执行顺序，以及现有 TTFT、TPOT、decode tokens/s 分别包含什么。特别说明文本解码、终端输出、停止 token 和收尾 forward 对计时的影响。

初始范围使用本地 Qwen3-8B-AWQ、GPU、单序列、关闭 thinking、一个短提示词。输出 token 上限先设为 16，同时核对实际生成数量。

交付：在对话中确定测量口径，不生成文件。确认理解后再进入基线测量。

### 2. 建立最小基线

只创建一份固定提示词 `profile/prompt.txt`，运行现有 Release demo，将构建参数、计时口径和测量结果写入 `docs/baseline.md`。原始日志留在 `profile/`。先做一次短跑确认程序与输入，再按需要做一轮预热和三轮测量。

解释实际工作量、TTFT、TPOT、decode 吞吐量及轮次间波动。模型加载时间与请求计时分开说明，区分模型 decode 指标和实际文本输出速度。

完成条件：输入、上下文起点、生成数量和构建配置明确，能够重复得到接近的结果。只分析这一份基线，暂不启动 profiler。

### 3. 用 Nsight Systems 定位主要耗时

复用固定提示词，只采集一段短执行，以本次改动的独立名称保存 `.nsys-rep`，保留用于对比的旧报告。先查看时间线，区分初始化、prefill、decode、采样和收尾，再选取 decode 区间看累计耗时。

结合 kernel、拷贝和 CPU API 的关联解释等待发生在哪里。没有 NVTX 标记时，用采样边界及 forward 调用计数辅助划分，并说明这种方法的范围。API 等待时间与 GPU 执行时间可能重叠，不能直接相加。

完成条件：明确一个优先分析的热点，给出它在所选区间中的耗时和占比。此时不修改源码。

### 4. 用 Nsight Compute 分析一个热点

根据上一步的数据选择一个代表性 kernel 及实际输入形状，只采集少量调用，保留 `profile/kernel.ncu-rep`。先看执行时间、线程组织、实际 occupancy、计算吞吐与内存吞吐，再按具体疑问补充指标。

交付：解释测量证据支持什么、还有哪些不确定性，提出一个可验证的优化假设。NCU 重放会改变运行状态，其中的 demo tokens/s 不作为性能基线。

### 5. 讨论一次改动

围绕单个热点，说明当前执行方式、拟修改的线程或数据组织、预期减少的成本，以及可能影响的数值行为。用热点占比估算端到端收益上限。

交付：一个具体的改动方案和对应验证方法。用户明确要求实现后，再进入下一步。

### 6. 实现并验证这个改动

只实现上一步选定的改动，运行与该改动直接相关的验证。涉及归约或运算顺序时，比较固定 token 序列上的数值误差；涉及采样或缓存时，验证对应行为。按实际覆盖情况说明通过、失败和跳过。

完成条件：改动可以独立审阅，相关正确性检查通过，再进行性能对比。

### 7. 用相同负载复测

复用原来的提示词、构建配置、上下文起点及生成数量，在不挂 profiler 的情况下测量，输出写入 `profile/after.log`。比较绝对耗时、吞吐量与波动，检查收益是否超出测量噪声。

交付：解释改动是否达到预期，决定保留、调整或撤回。只有需要验证瓶颈是否转移时，才重新采集对应报告；不自动开始第二项优化。

## 文件约束

结论保存在仓库文档，提示词、原始日志和报告放在 Git 忽略的 `profile/`，不随克隆分发。文件按需要创建，当前已有产物与可选的下一项产物如下：

| 文件 | 用途 |
| --- | --- |
| `docs/baseline.md` | 受版本管理的原始基线、两轮优化结果与测量口径 |
| `profile/prompt.txt` | 唯一的固定输入 |
| `profile/timeline_base.nsys-rep` | 原始实现时间线 |
| `profile/timeline_gemmv.nsys-rep` | 仅 INT4 GEMV 阶段的时间线 |
| `profile/timeline_gemmv_v2.nsys-rep` | INT4 + BF16 GEMV 阶段的时间线 |
| `profile/after.log` | 最新一轮无 profiler 原始输出；历史数值保留在文档中 |
| `profile/kernel.ncu-rep` | 可选：下一次实际开展 NCU 分析时才创建 |

命令和结论直接在对话中解释，必要时更新本计划。不默认生成 CSV、JSON、额外日志、分析脚本或自动执行整套流程的脚本；确有分析需要时，再说明用途并控制产物数量。

下一次从已有基线和热点证据出发，先选定一个待验证的问题，再决定是否补充采集或实现改动。
